The Problem

Why This Matters

Stack overflow is the #1 cause of mysterious crashes in embedded systems

⚠️

Existing Tools Fall Short

GCC -fstack-usage Per-function only, no call chain
Clang -Wframe-larger-than Per-frame only, no call chain

Neither tells you "main→A→B→C uses 48KB of stack total" — which is what embedded developers actually need.

💥

Real-World Impact

  • 1-8 KB Typical RTOS task stack size
  • #1 Cause of crashes in embedded systems
  • Silent Memory corruption from overflow
  • 0 Compilers provide call-chain analysis
✅

Our Solution

An LLVM-native whole-program analysis that:

  • Computes per-function stack frames via MachineFunction
  • Constructs the full static call graph
  • Reports worst-case cumulative stack depth
  • Detects recursion & handles indirect calls
  • Flags paths exceeding configurable thresholds
Architecture

How It Works

Three-stage pipeline: Extract → Collect → Analyze

01
📄

Source Code

C/C++ source files from embedded projects (FreeRTOS, Zephyr, bare-metal)

clang -emit-llvm ↓ .ll (LLVM IR)
02
🔍

stack-extractor

Scans LLVM IR for CallBase instructions, resolves direct calls and captures indirect call signatures

C++ (IR-level) ↓ call_graph.json
03
⚙️

stack-size-collector

Runs LLVM's full codegen pipeline (ISel → RA → PEI) and hooks a MachineFunctionPass to read MachineFrameInfo::getStackSize()

C++ (Backend) ↓ stack_sizes.json
04
📊

analyzer.py

Graph propagation solver: DFS with memoization, Tarjan's SCC for recursion, worst-case path reconstruction

Python CLI ↓ Rich Console Output
